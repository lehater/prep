# Bounded research workflow

1. Read the current topic framing, questions, experiments and relevant findings before proposing a change.
2. Investigate one precise question with competing interpretations, a discriminating example, negative cases, a falsifier and an explicit evidence level.
3. Distinguish owner-confirmed **research input**, reproducible desk result, unperformed test and accepted **engineering** decision. Never silently promote between levels.
4. Update only the topic's open-questions and open-experiments registers for live states. Update a concise findings document when useful; do not retain superseded models, obsolete fixtures, chronological duplicates or error retrospectives in the active workspace.
5. Keep a semantic subject relation separate from graph edges, UI filters/selections, import/storage shapes and inferred human proficiency.
6. Once evidence supports a concrete owner choice, record the choice in the proper research register. Any changes to current Product/Domain/Interface engineering meaning must then use the repository's routed Harness process, independently of this research workflow.

Avoid inventing new research tasks when an existing open question contains the same decision. The next step is evidence or a choice that actually changes what can be decided.
