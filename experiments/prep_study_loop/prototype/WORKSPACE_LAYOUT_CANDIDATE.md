# Prep workspace layout — согласованные L0/L1 и верхнеуровневый L2 (исследовательская компоновка)

**Классификация:** Owner-confirmed **UI layout input for exploration**, 2026-10-13; **не** Harness-accepted Presentation/System design, не утверждённый production UX и не результат пользовательского эксперимента. Это исходная компоновка для следующего обсуждения/прототипирования, **пока не реализована** в EX-PLD-06 prototype. Не менять канонические interface/architecture/domain-артефакты по этому документу без штатного решения и маршрута Harness.

**Источники:** обсуждение с владельцем проекта 2026-10-13; ранее существующие [Presentation System](https://github.com/lehater/prep/blob/main/docs/interface/presentation-system.md), [Screen/View Design](https://github.com/lehater/prep/blob/main/docs/interface/screen-view-design.md), эксперимент [knowledge_representation](https://github.com/lehater/prep/tree/main/experiments/knowledge_representation), реализация [KnowledgeExplorerFeature](https://github.com/lehater/prep/blob/main/frontend/src/features/knowledge-explorer/KnowledgeExplorerFeature.tsx). Эти ссылки — ориентиры, **не** доказательство текущей канонической применимости на исследовательской ветке. При расхождении проверять актуальную ветку, постановку EX-PLD-06 и Harness.

## L0 — неизменяемая оболочка

- **Десктопное приложение/workbench, не лендинг:** оболочка занимает доступный viewport; не использовать длинную прокручивающуюся страницу как базовую композицию.
- **Слева** постоянная **максимально узкая** навигация: ширина только для иконок, читаемых подписей и необходимых отступов, без запасной пустоты; свободное место отдаётся workspace. Минимум исследуемых разделов: **Цели / Capabilities / Знания / Материалы**. «Состояние» и другие разделы — открытая возможность, не обязательство.
- **Сверху** компактная строка приложения (текущее местоположение/контекст). **Над рабочими панелями** — постоянная зона контекста, поиска и фильтров текущего раздела. Она доступна даже при максимизации любой панели.
- **Снизу** возможна компактная статусная строка, не конкурирующая с рабочими панелями.
- Навигация заменяет содержимое workspace, но не боковую панель, строку приложения или область фильтров.

## L1 — одинаковая компоновка для всех сущностей

```text
┌───────────────┬─────────────────────────────────────────────────────────┐
│               │ Компактная верхняя строка: Prep / Раздел / Контекст     │
│ Постоянная    ├─────────────────────────────────────────────────────────┤
│ боковая       │ Фильтры раздела, поиск, сквозной контекст, сброс        │
│ навигация     ├───────────────────────────────┬─────────────────────────┤
│               │ [1] Основная таблица          │ [3] Детали выбранной    │
│ Цели          │ сущностей раздела             │     сущности           │
│ Capabilities  │                               │                         │
│ Знания        ├───────────────────────────────┤─────────────────────────┤
│ Материалы     │ [2] Связанные сущности         │ [4] Граф текущей        │
│               │ вкладки типов связей          │     выборки            │
│               │                               │                         │
│               ├───────────────────────────────┴─────────────────────────┤
│               │ Возможная компактная строка состояния                   │
└───────────────┴─────────────────────────────────────────────────────────┘
```

- **[1] и [2] имеют строго одинаковую ширину и общие левую/правую границы**. Между ними горизонтальный разделитель.
- **[3] и [4] образуют правую колонку на всю высоту workspace**, без расширения [2] под панель [3]. Между двумя колонками один общий вертикальный разделитель; внутри правой колонки — горизонтальный.
- **[1]** показывает множество объектов выбранного типа в табличном формате по умолчанию; **[2]** показывает связанные с выбранной строкой объекты одной категории за раз, с вкладками «Знания (N) / Цели (N) / Материалы (N)» — состав по фактически доступным отношениям.
- **[3]** показывает **собственные** свойства, название/описание и допустимый контекст выбранного объекта без дополнительного открытия карточки. Сводки отношений, дублирующие [2], пока не проектируем.
- **[4]** — *опциональное* графовое представление той семантической области, для которой есть обоснованные связи. Для Knowledge рассматриваем прежде всего **Knowledge–Knowledge**, а не автоматически Goal–Capability–Knowledge. Граф Capabilities, Materials либо межтиповой граф **не утверждены**. Сам выбор объекта **не должен скрыто сужать фильтр или менять набор узлов**.
- У всех содержательных панелей собственная прокрутка. Одновременно сохраняются список, связи, детали и граф (если граф включён).

### Управление панелями — общий механизм

Для **каждой** из четырёх панелей одинаковые операции:

1. **Выбрать/использовать** содержимое обычным способом.
2. **Свернуть**, не закрывая: остаётся компактная видимая полоса/заголовок и кнопка восстановления. Освободившееся место получают соседние панели. Панель и выбранный контент не уничтожаются.
3. **Максимизировать** на весь *workspace ниже фильтров и справа от sidebar*. Верхняя строка, постоянная навигация, фильтры и другой shell остаются видимы. Максимизирована максимум одна панель.
4. **Восстановить** прежнее размещение, размеры, свёрнутость остальных панелей и контекст выбора.
5. **Изменить размер границей**: перемещаемый общий вертикальный разделитель между колонками, горизонтальные разделители [1]/[2] и [3]/[4]. Нужны разумные минимальные размеры, чтобы заголовки и восстановление не пропадали.
6. **Сбросить компоновку** в начальное состояние отдельной командой (предложенный удобный механизм).

Никакая максимизация не перекрывает фильтры; поиск и фильтрация продолжают воздействовать на развёрнутую таблицу/граф. Для панелей [2]/[3] общая зона фильтров остаётся на месте, даже если для них дополнительные фильтры пока не нужны.

### Навигация, фильтры и выбор

- Сквозной контекст (например, выбранная цель) и фильтры списка — **разные** состояния. Контекст перехода отображается явно и снимается пользователем.
- **Один общий выбор объекта текущего типа** для таблицы [1] и соответствующего графа [4]: клик в любом из них немедленно синхронизирует выделение в другом, обновляет [2] и [3]; изменение источника выбора не меняет раздел или фильтры. Это требование **к будущему работающему интерфейсу**, а не декоративный эффект wireframe. Наведение временно подсвечивает, но не заменяет выбор.
- Клик по строке связанного объекта в [2] **открывает его тип сущности** в основной таблице нового раздела с автоматически применённым фильтром исходного отношения. Например: **G01 → C02** открывает раздел Capabilities со scope по G01; далее переход из C02 к K04 открывает Knowledge со scope по C02.
- У одного Knowledge могут быть связи с несколькими Capabilities; связь в UI **не** означает исключительную иерархию или доказательство обязательности/компетентности.
- Количество вкладок связанных коллекций соответствует модели, принятой впоследствии; не создавать неутверждённые типы отношений.

## Исходные размеры — только варианты для проверки

- Sidebar — **минимальная ширина по содержимому** (для проверки ориентир порядка 130–145 px, не норма); верхняя строка ~48 px; статусная строка ~30 px.
- Левая/правая колонка **65/35** с перемещаемой границей.
- Высота основной/связанной таблиц приблизительно 55/45; высоты деталей/графа уточняются.
- Пиксели, процентные доли и адаптивные минимумы **не являются жёсткими требованиями**. Приоритет — смысловая иерархия и контроль пользователя.


## L2 — крупные решения о графовом механизме (Owner exploration, 2026-10-13)

- **Базовая богатая проекция — Knowledge–Knowledge:** знания потенциально имеют разные типы; отношения между знаниями тоже типизированные, могут быть направленными. Конкретный словарь типов/отношений **не выбирался**; K–K рёбра не следует выдумывать из C–K scope, из текстового соседства или из UI-геометрии. Текущий EX-PLD-06 fixture не задаёт реальных K–K рёбер.
- **Универсальный механизм**, не обязательный «граф всего»: тип узла, тип/направление ребра, метки/легенда, семантический поиск, выбор, подсветка, фильтры, рабочая выборка и навигация. Отображать межтиповые отношения только при обоснованном сценарии, не потому, что сущности существуют в одной модели.
- **Различимые визуальные каналы**: класс узла можно показывать формой, подтип цветом/маркером; тип ребра — стилем и/или цветом, направление стрелкой при направленной семантике, смысл — tooltip/выбираемой подписью и текстовым инспектором. Цвет **не должен сам по себе** означать и тип, и оценку/состояние обучения; легенда компактная. Это возможности компонента, не утверждённая палитра или таксономия.
- **Единое состояние выбора** на уровне workspace: выбранный узел текущего раздела синхронизирован с [1], [2], [3], [4]. Выбор узла и его фокус/центр камеры — **разные** действия; hover — временная подсветка. Выбор ребра открывает его направление/тип/смысл, но детали inspector ещё открыты. Клик по узлу *другого* типа: межраздельную навигацию отдельно согласовать, не выполнять скрыто.
- **Граф не должен перефильтровываться от выделения**. Отдельные команды могут показывать обзор, локальное окружение выбранного знания или последовательное расширение с возвратом к предыдущему контексту; это **кандидатные режимы**, не утверждённая окончательная механика.
- **Масштабирование — сначала смысловое**: поиск → фокус → окружение → расширение по запросу, ограниченная выборка и полнофункциональный не-графовый путь. Не предполагать, что весь корпус обязан одновременно помещаться в панель.
- **2D/3D, виды графов C–C/Material–Material и смешанные графы не выбраны**. Упоминание графа в L1 — резерв исследовательской поверхности, не обязанность отображать его в каждом разделе.

### Технический донор и предел доказательств

Исторический [Knowledge Representation experiment](https://github.com/lehater/prep/tree/main/experiments/knowledge_representation) содержит 3D renderer, выбор/фокус, поиск, подсветку соседей, фильтрацию типизированных отношений, legend, camera-fit/reset, instanced nodes, batched links/arrowheads и остановку idle-rendering. Сценарии нагрузки: 60/90, 250/375, 1000/1500 узлов/рёбер. В [старом протоколе](https://github.com/lehater/prep/blob/45c193ac0a50b6023a29e9a87f404b794a24a955/docs/research/knowledge-representation-experiment.md) описаны машинно-зависимые ~25–30 RAF FPS на оптимизированном 1000/1500. Это **донор технической осуществимости**, не проверка полезности, не целевые требования производительности и **не** свидетельство проверки 5000 узлов. Старая 3D-first гипотеза и прежняя онтология не переносятся автоматически.

Вопросы и исследования держать в [реестре вопросов](../../../docs/research/product-learning-direction/open-questions.md) и [реестре экспериментов](../../../docs/research/product-learning-direction/open-experiments.md); результаты концептуального обсуждения и границы вывода — в [исследовательском checkpoint](../../../docs/research/product-learning-direction/interface-exploration-checkpoint-2026-10-13.md). Эти файлы не заменяют Harness и не утверждают production UX.

## Состояние компоновки — решение частично открыто

**Согласовано:** максимизация/восстановление возвращает предыдущие размеры в текущем сеансе работы; переходы между разделами не должны произвольно разрушать выбранную компоновку. **Ещё не выбрано:** сохранять ли размеры и свёрнутость после закрытия и повторного открытия приложения. Без отдельного решения использовать простую сессионную память и понятную команду сброса; не объявлять долговременное сохранение требованием.

## Граница следующего этапа (Owner priority correction, 2026-10-13)

Этот wireframe решает структуру workspace, но **не** является готовой концепцией Prep. Следующая работа — составить согласованную исследовательскую модель взаимодействия **всех четырёх разделов** на реалистичных взаимосвязанных примерах и пройти сквозные кликабельные сценарии: выбор Goal, C-контекст, K/K–K связи, материалы, выбор/выгрузка, возвращение к исходному контексту. Спорные типы отношений и смысл Capability фиксировать как вопросы, не домысливать. До готовности целостной концепции и удобного браузерного прототипа пользовательский сравнительный EX-PLD-06 **отложен**; [Q-PLD-16](../../../docs/research/product-learning-direction/open-questions.md), [EX-PLD-09](../../../docs/research/product-learning-direction/open-experiments.md), [checkpoint](../../../docs/research/product-learning-direction/interface-exploration-checkpoint-2026-10-13.md).

## Ограничения и последующая проверка

- Сначала согласовать wireframe и информационную иерархию; **не** начинать реализацию frontend на основании одного этого файла.
- Детальную раскладку полей [3], колонки [1]/[2], пиксельные размеры, поведение узкого окна и тонкости графовой навигации **отложить**, пока они не нужны для целостного пользовательского сценария. **Раньше EX-PLD-06 сравнивать не следует:** сперва согласовать объединённую концепцию Goal / Capability / Knowledge / Materials, проверить связные кликабельные сценарии, затем реализовать пригодный браузерный прототип; только после этого обсуждать пользовательское сравнение. Не делать графовую технологию или точную геометрию искусственным препятствием, но обеспечить реальный смысловой переход между разделами.
- Это **паттерн интерфейса**, а не решение о продуктовых возможностях. В EX-PLD-06 сохранять экспериментальные различия A/B/C и информационный паритет, не добавлять структурную навигацию в C только ради унификации и не считать этот документ результатом пользовательского теста.
