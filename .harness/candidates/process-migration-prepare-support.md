# Application Process — Prepare Missing Support

## Purpose

Define one bounded occurrence that turns a learner-visible missing-support need plus fragmented source material into independently accepted owner-scoped support and an explicit unresolved/rejected remainder.

The process references accepted Application operations and semantic owners. It does not make the learner responsible for corpus/schema maintenance and does not invent one global cross-owner transaction.

## Occurrence boundary

One occurrence starts when the learner initiates a missing-support request with motivating target/focus context and available source material.

It ends when the occurrence returns to the originating preparation work with the accepted usable support now available and any remaining preparation gaps explicit, or when continuation is explicitly unavailable/abandoned.

## Referenced work

The occurrence references:

- `APP-REQUEST-PREPARATION-SUPPORT`;
- `APP-PREPARE-SUPPORT`.

Owner-specific semantic acceptance performed inside `APP-PREPARE-SUPPORT` remains owned by the corresponding tactical semantic owner.

## Composition

The request establishes motivating context and source provenance before preparation work is attempted.

Preparation may produce independently valid owner-scoped results. Accepted results remain usable while unsupported, conflicting or incomplete candidates remain unresolved/rejected. Returning to the origin uses the resulting support plus explicit remainder; no global all-or-nothing acceptance is implied.

## Continuation and correlation

A paused occurrence may continue when additional source material becomes available or an unavailable dependency returns, provided the motivating target/focus context is still semantically usable.

Correlation is the preparation request plus motivating context and source provenance. Runtime job ids or workflow-engine tokens are not canonical process identity.

If the target/focus basis materially changes, the occurrence refreshes/reconsiders before applying a dependent continuation.

## Recovery

Accepted owner-scoped semantic results are not rolled back merely because another candidate remains unresolved or rejected.

`DEPENDENCY_UNAVAILABLE` preserves the request, source provenance and motivating context for later continuation. There is no process-level automatic retry or compensation across semantic owners.

## Progress

No independent ProcessState is required. Accepted owner results plus explicit unresolved/rejected remainder are sufficient to derive meaningful progress.

## Completion

A successful occurrence completes when the learner can return to the originating preparation work with all justified accepted support plus an explicit remainder.

Completion does not require every requested semantic candidate to be accepted. A fully unresolved/rejected result is still an explicit completed outcome when no usable support was established and the remaining gap is visible.
